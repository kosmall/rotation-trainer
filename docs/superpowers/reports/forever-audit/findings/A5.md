# A5: consistency of calculation paths (findings)

Auditor A5, 2026-11-28. Read-only audit; nothing outside this file was changed (`git status` clean, no files left in `reports/`).
Reproduction scripts live in the scratchpad `/tmp/claude-0/-home-user-rotation-trainer/05276e97-9c03-5b59-93ad-fdb2660cdf40/scratchpad/` (`t1.ts` ... `t15.mts`, `ui1.test.tsx`, `vitest.scratch.config.ts`); run with `npx tsx <file>` from the repo root (the UI one with `npx vitest run --config <scratchpad>/vitest.scratch.config.ts`). id: A5-003
obszar: A5
waga: medium
status: confirmed
tytuł: The "common random numbers" do not pair the sessions: one RNG stream per pull is consumed in event order, so any difference between the two runs (another spell, +5 spell power) desynchronises it and the paired sessions are almost uncorrelated; the UI and the EP code claim narrow intervals "because of the same seeds".
dowód: `src/forever/fight.ts:142` (single `createRng(seed)`; `rng.next()` for crits, misses, Nightfall, pet hits, pushback in event order, e.g. `fight.ts:380, 388, 450, 456, 670, 680, 737`); claims: `src/ui/forever/CompareView.tsx:58` ("oba grają na tych samych seedach, więc różnice mają wąskie przedziały ufności"), `src/forever/ep.ts:1-3` ("the simulation noise cancels"), `src/forever/duel.ts:1-2`. Repro `t9.mts` (200 sessions, level 50, same seeds, kills/h per session): correlation between AFF_WRACK and DEMO_PACT_R1 = -0.090. Repro `t10.mts` (base vs changed stat on the same seeds):
```
AFF_WRACK SP+40 corr(base, changed) -0.083  sd(diff)/sqrt(sd(a)^2+sd(b)^2) 1.04
AFF_WRACK SP+5  corr 0.222  ratio 0.88
AFF_WRACK int+40 corr 0.193 ratio 0.90
DEMO_PACT_R1 SP+40 corr 0.149 ratio 0.94
DEMO_PACT_R1 SP+5  corr 0.410 ratio 0.79
```
(ratio 1.0 = no gain from pairing; a +5 spell power step, which should be almost the same fight, is only correlated 0.2-0.4.)
oczekiwane vs rzeczywiste: with real common random numbers the variance of the paired difference is much smaller than the sum of the two variances; actual: about equal. The intervals are valid but as wide as for independent runs, so EP weights (e.g. AFF_WRACK crit weight 2.38..8.87 at 60 sessions, `t6.mts`) and duel verdicts need 4-10x more sessions than the text suggests.
wpływ na wyniki: no bias; precision. Many "≈ (not significant)" and EP "n/a/wide" results are noise, not information. Applies to duel, ranking `vsBest`, EP, discover ("tiedWithFirst", insensitivity) and the optimizer.
proponowana poprawka: give each random source its own stream derived from the pull seed (player crit, player miss, procs, mob, pet, pushback), or draw by a counter-based hash `(seed, mobIndex, eventKind, k)` so that a missed/extra event of one kind does not shift the others. Then re-measure the correlation (target above 0.8 for +5 SP) and keep the text only if it holds. Changes all simulated numbers slightly (new random draws): treat as a separate, last wave and give the before/after table.
pliki do zmiany: src/forever/fight.ts (+ text in CompareView.tsx, ep.ts if left as is)
zależy od / koliduje z: every fix that changes results (do after them); A1 (fight.ts owner)

id: A5-013
obszar: A5
waga: low
status: confirmed
tytuł: Statistics: the paired 95% interval uses the normal 1.96 at any sample size, significance is decided per level without multiplicity, and the "crossover" is the first flip of the per-level verdicts; with the UI minimum of 5 sessions about 8-12% of identical-build comparisons come out "significant".
dowód: `src/forever/duel.ts:76` (`1.96 * std / sqrt(n)`), `ep.ts:313`, `discover/engine.ts:219`; `duel.ts:115-122` (crossover); UI minimum `src/forever/web/api.ts:74` (5). Repro `t9.mts` (the same build split into independent halves, level 50, 1200 sessions):

```
n 5   false-significant 10 / 120  8.3%
n 10  false-significant 3 / 60    5.0%
n 30  false-significant 1 / 20    5.0%
n 100 false-significant 0 / 6     0.0%
```
(small counts; the theoretical rate for t(4) with z=1.96 is about 12%.) Across a 50-level sweep about 2-3 levels will show a false winner at the nominal 5%, and one such level creates a "crossover".
oczekiwane vs rzeczywiste: at least t-quantiles for small n; crossover robust to a single significant level.
wpływ na wyniki: spurious "winner" labels at low session counts and in long sweeps; the UI default (60) is fine.
proponowana poprawka: use Student t for n < 30 (or raise the UI minimum to 20), define the crossover as the first level after which the winner stays the same for k levels, and label the sweep verdicts as per-level.

## Uwagi spoza zakresu

- A3: `Demonic Embrace` is applied as `+3% Stamina per rank` with a hard-coded `0.03` in `src/forever/stats.ts:137`, while `talents.json` carries `maxHpMultPerRank: 0.015` (verify) that no code reads; the in-game text (`src/data/classes/warlock/talentDescriptions.json`, "+3% Stamina, -1% Spirit" per rank) also lowers Spirit by 1% per rank, which is not modelled (the Forever source cited in `talents.json` mentions only Stamina). Decide which is right and make data and code one source.
- A2/A1: EP of Spirit is negative for affliction builds at 60 sessions (AFF_WRACK L50 spirit -0.30, CI -0.67..-0.04) because the Life Tap health cost is `rank base + life_tap_spirit_coeff * Spirit` (`stats.ts:169-171`, assumption `verify`), so more Spirit costs more HP per tap and more breaks. A modelling artefact of the unverified Life Tap formula, worth a note in the report.
- A1: `DEMO_PACT_MAXRANK` at level 30 plays at 54 kills/h while the other Demonology builds play at 88-89 (`t3.ts` output), a large step that looks like a rank/mana threshold effect (Shadow Bolt max rank at level 30); not analysed.
- A1: `simulatePull` defaults `ranks = cfg.ranks ?? ranksAt(variant, level)` (`fight.ts:143`) and ignores a legacy perk / respec options because `PullConfig` has no `picks`; harmless for `runCell` (always passes `ranks`) but a trap for direct callers (scripts/addon-*.ts, tests).
- Architecture: `src/forever/ep.ts` imports `MAX_LEVEL/MIN_LEVEL` from `src/forever/web/api.ts`, which imports `planEp` from `ep.ts` (a cycle; works because the constants are read inside a function); level limits 10-59 are duplicated (`api.ts`, `ep.ts` messages) while discover allows 10-60.
- Docs: `docs/forever-data-ledger.md` section 3 ("Wrack: 60 at level 40, 124 at level 60") and section 6 ("out-of-combat HP regeneration taken as zero") are superseded by sections 7-8 and the code; a reader of section 3/6 gets a wrong picture.
- `forever:discover --profile mine` (or any unknown profile) is not validated in the CLI; the error appears inside the workers (`stats.ts:81, 85`), after the warm-up.
- `parseBuild` (`web/custom.ts:276`) maps a missing `pet` to `'succubus'` and an unknown `rotation` to `'demonology'` silently; an exported JSON edited by hand can change the build without a message.
